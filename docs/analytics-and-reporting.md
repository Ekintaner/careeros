# Analytics & reporting (CODEX-011)

`GET /api/v1/analytics?from=2026-10-01&to=2026-10-17&timeZone=Europe/Kyiv&interval=week` requires the existing authenticated session. No owner identifier is accepted. All entity queries use OwnedData; the parameterized duration SQL explicitly scopes both application and history owners. Responses contain aggregate labels and counts only. Reads share a PostgreSQL repeatable-read snapshot.

## Semantics

- Default is the last 90 local calendar days in UTC. From/through dates are inclusive, converted independently to UTC boundaries with an exclusive next-day end. IANA zones and UTC are accepted. Missing or ambiguous midnight boundaries return 400. DST days can be 23 or 25 hours. Ordered ranges are limited to 732 days; malformed input returns 400.
- Application cohort: records **created** in the date range, including archived records. Stages/outcomes are current, not historical snapshots. Applied is cohort records with an applied timestamp, including corrected dates outside the selected creation period.
- Both conversions divide by **distinct cohort applications with AppliedAtUtc**. Interview numerator counts an application once if it has an Interview status event OR any current scheduled interview record. Future scheduled interviews qualify; attendance is not inferred. Offer numerator counts an application once only with an Offer history event. Accepted is not used to reconstruct missing Offer events. Zero denominator is N/A. Progression is measured through the response as-of instant, rather than capped at the cohort creation window.
- Weekly creation trends start Monday; monthly trends start the first. Local PostgreSQL day aggregates are rolled into calendar buckets; empty buckets are zero observed creations, not invented history. Edge buckets are partial.
- Company grouping uses company ID and current name (same names may appear twice); role grouping uses current exact title. Top 20 ordered by descending count then label; omitted groups are not an Other estimate. Company/role edits affect these current classifications.
- Stage durations use immutable history, partitioned by application and ordered by sequence. Only adjacent sequence pairs with nonnegative elapsed times count. Each completed visit is a sample, including repeated visits and archive/restore visits. Open visits, missing predecessor intervals and missing history are excluded. A zero-day sample is valid. The mean is elapsed UTC days, not local calendar days. No history is backfilled.
- Interviews are independently filtered by scheduled start, classified past only when scheduled end <= as-of. Upcoming includes in-progress. Outcomes are free text and not interpreted as success. Tasks are independently filtered by creation; current completed/overdue/open categories are disjoint. Overdue means incomplete and due < as-of; undated tasks are open. Reopening removes completion evidence; historical task throughput cannot be derived.

## Bounds, cost and limits

Eight fixed aggregate queries, no per-record query loop, no raw application/history list fetched into application memory. Daily aggregates are bounded by the validated date range; groups by stages/task/interview states are finite; company/role results are capped at 20. Duration aggregation runs in PostgreSQL with a window function. Queries have cancellation and existing database command timeout. Work grows with the owner's matching data; no persisted rollups or new index/migration is introduced. Existing owner, foreign-key and history sequence indexes remain in use. No package, paid analytics, AI, SaaS, external telemetry or additional mandatory cost.

The accessible tables contain the exact counts behind decorative bars. Loading, retry, empty cohort, missing duration and zero-denominator states are explicit. Filters are labeled and keyboard operable; narrow layouts wrap. No CSV/PDF export, historical company/role snapshot, deleted-record recovery, attendance inference or predictive analytics is provided.
